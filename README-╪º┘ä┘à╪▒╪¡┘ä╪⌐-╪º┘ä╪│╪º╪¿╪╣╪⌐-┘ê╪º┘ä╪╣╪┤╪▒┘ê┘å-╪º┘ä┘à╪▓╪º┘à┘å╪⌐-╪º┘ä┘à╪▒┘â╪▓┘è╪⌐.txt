# سوبر العراق IQ — المرحلة 27: المزامنة المركزية الآمنة

هذه المرحلة تبني على أرشيف المرحلة 26، وتضيف حماية من الكتابة المتزامنة على نفس الفرع وسجل إصدارات للنسخ السحابية.

## ما الذي تغيّر؟
- رفع نسخة الفرع صار يعتمد على دالة PostgreSQL ذرّية `push_branch_snapshot` مع قفل صف الفرع وفحص رقم الإصدار؛ هذا يمنع جهازين من استبدال تحديثات بعضهما بصمت.
- عند وجود تعارض يرجع الخادم HTTP 409 ولا يكتب فوق النسخة الأحدث.
- حفظ سجل الإصدارات والنسخ في `branch_snapshot_history`.
- إضافة endpoint لعرض بيانات وصفية عن آخر الإصدارات: `GET /api/sync/history?limit=20` (لا يعرض محتوى النسخ).
- قبل استعادة السحابة من الواجهة، ينزّل المتصفح نسخة JSON محلية من البيانات الحالية.

## التثبيت / التحديث
1. خذ نسخة احتياطية من مشروع Supabase الحالي.
2. افتح Supabase SQL Editor.
3. إذا لم تكن قد طبّقت المخطط الأساسي، نفّذ `server/supabase-schema.sql` كاملاً. وإذا كان مخطط المرحلة 26 مطبقاً، نفّذ فقط `server/supabase-phase27.sql`.
4. أعد تشغيل الخادم Node.js. لا تضع `SUPABASE_SERVICE_ROLE_KEY` أو رموز الفروع داخل واجهة المتصفح أو تشاركها مع الموظفين.
5. اختبر جهازين على نفس الفرع: ارفع من الأول، ثم حاول الرفع من الثاني بإصدار قديم؛ يجب أن يرجع 409 ولا تُستبدل بيانات الجهاز الأول.

## حدود مهمة
- المزامنة الحالية تحفظ لقطة JSON كاملة لكل فرع؛ ليست بعدُ سجل أحداث/معاملات موزعاً، ولا تنفّذ دمجاً تلقائياً لتغييرات الجهازين. عند التعارض يجب سحب النسخة الأحدث ومراجعة الفروقات قبل المتابعة.
- جدول سجل النسخ يحتفظ باللقطات السابقة، لذلك راجع سياسة الاحتفاظ والحجم والتكاليف قبل الإنتاج. لا توجد واجهة لاستعادة إصدار تاريخي في هذه المرحلة.
- هذه المرحلة لا تضيف بعدُ تسجيل دخول مركزي للموظفين أو صلاحيات لكل عملية داخل API؛ يجب إنجاز ذلك واختباره قبل الاستخدام التجاري متعدد الفروع.
- لم يتم الاتصال بمشروع Supabase فعلي أو اختبار نشر سحابي من هنا؛ يلزم تنفيذ SQL وإعداد أسرار مالك النظام ثم إجراء اختبار قبول فعلي.
