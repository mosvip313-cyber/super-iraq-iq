سوبر العراق IQ — المرحلة 41
عمليات مالية مستقلة على الخادم وقيود فريدة للفواتير والمحاسبة

الملفات الجديدة:
- server/supabase-phase41-financial-operations.sql
- تحديث server/src/server.js
- تحديث apps/admin-web/cloud-integration.js

ما توفره المرحلة:
1) واجهة API للخادم POST /api/financial/sales و /api/financial/collections و /api/financial/expenses.
2) كل طلب يتطلب operationId ثابتاً (16-100 حرفاً). عند إعادة المحاولة يجب إرسال نفس operationId ونفس المحتوى.
3) تسجيل ذري داخل PostgreSQL باستخدام RPC ومعاملة قاعدة البيانات، مع قفل استشاري لكل فرع ومعرّف عملية.
4) قيد فريد لكل (branch_id, operation_id)، ولكل رقم فاتورة حسب نوع المستند، ولكل سطر قيد محاسبي للعملية.
5) إعادة نتيجة العملية السابقة عند تكرار نفس المعرّف ونفس المحتوى؛ رفض المعرّف نفسه إذا تغير المحتوى؛ ورفض رقم الفاتورة المكرر.
6) إنشاء قيود محاسبية أساسية للمبيعات والتحصيلات والمصاريف. المبالغ المخزنة في الحسابات بالدينار العراقي (IQD)؛ يجب تحويل USD إلى IQD والتحقق من سعر الصرف قبل إرسال الطلب.
7) واجهة تكامل بالمتصفح: siqNewFinancialOperationId() لإنشاء معرّف مرة واحدة، وsiqSubmitFinancialOperation(type,payload) لإرسال الطلب.

التفعيل:
1. خذ نسخة احتياطية.
2. نفّذ server/supabase-phase41-financial-operations.sql في Supabase SQL Editor بعد supabase-schema.sql وsupabase-phase27.sql وsupabase-phase40-idempotency.sql.
3. انشر إصدار الخادم المحدّث مع SUPABASE_URL وSUPABASE_SERVICE_ROLE_KEY ورموز الفروع الصحيحة. لا تضع service-role key داخل المتصفح.
4. أنشئ operationId مرة واحدة لكل فعل مستخدم؛ خزّنه مع الطلب المعلّق، وأعد استخدامه في كل retry. لا تنشئ معرّفاً جديداً عند انتهاء مهلة الاتصال.
5. اختبر على فرع تجريبي: إرسال الطلب نفسه مرتين، إعادة المعرّف بمحتوى مختلف، وإرسال رقم فاتورة مستخدم مسبقاً.

ملاحظات وحدود مهمة:
- هذه المرحلة تنشئ API مستقلاً وآمناً للتسجيل المالي، لكنها لا تغيّر بعد أزرار الحفظ الحالية في index.html لتستدعيه تلقائياً؛ التطبيق ما زال يعمل محلياً/أوفلاين، ويجب ربط واجهات البيع والتحصيل والمصاريف بهذه الواجهة في مرحلة دمج لاحقة قبل اعتبارها المصدر المالي الوحيد.
- لا يتم تحديث مخزون الفرع أو أرصدة العملاء والموردين تلقائياً من هذه الجداول في هذه المرحلة؛ التفاصيل تحفظ ضمن payload للتدقيق فقط. لا تخلط هذه السجلات بعد مع تقارير البيانات المحلية دون عملية ترحيل ومطابقة واضحة.
- القيود المحاسبية الأساسية لا تمثل نظام دفتر أستاذ متكاملاً ولا تغطي الضرائب أو تكلفة البضاعة المباعة أو القيود العكسية.
- لا يمكن تأكيد تنفيذ SQL على مشروع Supabase حقيقي من بيئة البناء هذه. اختبارات هذه الحزمة تقتصر على فحص صياغة JavaScript وفحص الأرشيف، لا اختبار تكامل حي أو تنافس فعلي بين مستخدمين.
