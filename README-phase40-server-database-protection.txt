سوبر العراق IQ — المرحلة 40
حماية المزامنة على مستوى الخادم وقاعدة البيانات

التغييرات:
1) أضيف endpoint المزامنة استخدام RPC جديدة push_branch_snapshot_idempotent.
2) أضيف جدول branch_sync_requests بمفتاح أساسي مركب (branch_id, request_id).
3) SQL يقفل طلب المفتاح نفسه بمعاملة/قفل advisory، ويرجع النتيجة السابقة إذا أعيد نفس الطلب بنفس المحتوى.
4) إذا أعيد استخدام request_id مع حمولة مختلفة، يرجع تعارضاً ولا يكتب snapshot جديداً.
5) تبقى آلية revision compare-and-swap الحالية فعالة لتمنع استبدال نسخة أحدث من جهاز آخر.
6) تكامل المتصفح يولّد requestId حتمياً من الفرع والإصدار ومحتوى snapshot، حتى تحمل إعادة محاولة نفس المحتوى نفس المفتاح.

خطوات التفعيل:
- خذ نسخة احتياطية من قاعدة البيانات والمشروع.
- افتح Supabase SQL Editor وشغّل server/supabase-phase40-idempotency.sql بعد server/supabase-schema.sql وserver/supabase-phase27.sql.
- انشر إصدار الخادم الجديد من server/src/server.js، ثم حدّث ملفات واجهة admin-web.
- تحقق من /api/health، ثم اختبر مزامنة ناجحة وإعادة إرسال نفس الطلب، وجرب جهازين على بيانات تجريبية.

الحدود المهمة:
- هذه الحماية تضمن idempotency لطلب مزامنة مطابق بنفس requestId، وتمنع تعارضات الكتابة على snapshot باستخدام revision.
- لا تعني بعدُ أن كل عملية بيع/تحصيل/صرف مستقلة تُنفّذ كأمر مالي منفصل داخل قاعدة البيانات؛ بنية التطبيق الحالية ترفع snapshot كامل من المتصفح. لضمان منع تكرار نفس الفعل التجاري حتى لو أنشأ جهازان عمليتين مختلفتين بمفاتيح مختلفة، يلزم نقل كل عملية مالية إلى API أوامر مستقل بمفتاح idempotency ثابت منذ بداية العملية، وتخزين الفاتورة/القيد في جداول مطبّعة ذات قيود UNIQUE داخل نفس معاملة قاعدة البيانات.
- لم يتم الاتصال بقاعدة Supabase حقيقية أو تشغيل اختبارات متزامنة في هذه البيئة. لا تعتمد التغيير قبل تطبيق الترحيل والاختبار على نسخة تجريبية.
